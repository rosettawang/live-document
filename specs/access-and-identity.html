Who gets in, and who is speaking

Status: done done · created Aug 5, 2026 · shipped Aug 5, 2026 · priority 15 · account step

Two small problems that are really one: a public URL that should not be fully public, and a shared document where "who changed this?" is the first question anyone asks.

What is actually at stake, stated plainly so the gate is sized correctly

The document contains four people's flight numbers, arrival times, where they are sleeping, and eventually booking references. It also holds a button that spends money from Rosetta's Anthropic account on every press. Neither of those is catastrophic if leaked, and neither should be left open. This is a passcode problem, not an auth problem — the failure mode is a stranger scribbling on a trip plan or running up $40 of tokens, not a breach.

Sizing it correctly matters in both directions: an OAuth flow here would be wasted work that does not ship by Thursday, and no gate at all is a guessable subdomain holding an itinerary.

The gate — type your name

The word is the login, and that removes a whole step

Rosetta, Aug 5, 2026: "passcode is either Ed or Kenia or Rosetta and then i know who is editing." The original design had a shared word plus a name to pick — two things to get right on a phone, and a name anyone could set to anything. Collapsing them means you type one thing and that thing is who you are. Nothing to choose, nothing to mismatch, and attribution becomes a property of getting in rather than an honour system on top of it.

Matching is a case-insensitive prefix, settled Aug 6, 2026: "they might add last name so as long as it starts with ed and kenia or rosetta." So Ed, ed, Ed Smith and Edward all arrive as Ed.

  1. Any request without a valid cookie gets gate.html: one text field, one button.
  2. POST /auth with the name. The Worker resolves it to a person, then sets a signed, HttpOnly, Secure, SameSite=Lax cookie holding {name, iat}, 30-day expiry — comfortably past the Aug 19 return.
  3. The WebSocket upgrade checks the same cookie. A gate on the HTML that leaves the socket open is not a gate, and it is the standard way this gets built wrong: the document is served through one check and then streamed through none.
  4. Unknown name: fixed 400ms delay, one generic message. The resolver checks every entry rather than returning on the first hit, and takes the longest match — so a two-entry person like Kenya resolves the same either way.
  5. The gate remembers where you were going, so a link straight to /packing survives signing in.

Login pass — set the crew list

npx wrangler secret put DOC_PASSCODE

Currently, and deployed Aug 6, 2026:

Rosetta:<match>,Kenya:<match>,Kenya:<alt-spelling>,Ed:<match>,Ben:<match>

The live values are not written down here on purpose — they are in the DOC_PASSCODE secret, and this folder is in a public repository. npx wrangler secret list confirms it is set; nothing but Cloudflare knows what it says.

Name:match pairs, comma separated. The left side is what shows in the margin and in presence; the right side is what someone types. Kenya has two entries because she writes Kenia and the trip document says Kenya.

Adding a fifth person is one command — append ,Ada:ada and re-run. No deploy, no code change. Same move to harden one person later if the document ever holds anything worth protecting: replace their right-hand side with something unguessable.

Note the cost of any change: cookies are signed with this secret, so editing it signs everyone out. They just type their name again — and since Aug 5 the page says so rather than silently failing.

Names, after a round trip through the alternative

Aug 6, 2026 — this is where it landed: you type your name. Matching is a case-insensitive prefix, so a surname is fine and so is any capitalisation. Kenya is registered under both kenia and kenya.

The reasoning below is kept because the trade-off is real and someone will re-propose the other side. It was tried, and rejected for good reason.

The impersonation argument, tried and overruledwhy names lose, and why that was still the right call

The obvious reading of "passcode is either Ed or Kenia or Rosetta" is that each person types their own name. It was built that way and it is wrong, for a reason that only shows up when you say it out loud: if Ed's word is "ed", then Ed's word is known to Kenya, Ben and Rosetta too. Any of the four can sign in as any other, so the attribution the feature exists to provide is decorative. Rosetta, Aug 5, 2026: "um ed should not be in as me."

Generated words fix it while keeping the property that mattered — one thing to type, and the thing you type is who you are. Each person is told only their own.

Residual, stated rather than hidden: whoever sets the secret can read every word, so Rosetta can still sign in as Ed. Closing that needs per-person credentials the server never sees, which is the accounts system this whole design exists to avoid. Among four friends planning a holiday, the line is drawn here deliberately.

Overruled Aug 6, 2026, and correctly. Generated words meant a second thing to remember, distributed one-to-one, for a document whose worst-case compromise is a stranger scribbling on a trip plan. The friction was certain; the threat was not.

Identity: a name, not an account

The word you type resolves to a name, which lives in the signed cookie and rides along with every mutation as updated_by. Nobody picks it; it falls out of signing in. That single field pays for itself three times over:

  • Attribution in the margin. "Ben · 14:20" beside a changed block, which is the difference between a document people trust and a document people argue about.
  • Presence. presence-and-history needs a label for the dots.
  • Rate limiting. claude-editor-contract meters AI calls per name per day, which is impossible without one.

It is a weak boundary and should not be dressed as a strong one. Anyone holding Ed's word is Ed as far as this document is concerned, and the person who set the secret holds everyone's. Among four friends planning a holiday that is the right place to stop; pretending otherwise would mean building the accounts system this spec exists to avoid.

Claude gets a name too

AI-written blocks are attributed to claude and rendered with a distinct marker in the margin. This is not decoration. When a rewrite is wrong — and some will be — the first thing anyone needs to know is whether a person wrote that sentence or a model did, before deciding whether to trust the price in it. It is also what makes undo legible: "revert Claude's change to this block" is a comprehensible action in a way that "revert to rev 47" is not.

Verification

  1. curl -sI https://<url>/ with no cookie → the gate, not the document.
  2. websocat or a fetch with Upgrade: websocket and no cookie → rejected. Test this one specifically; it is the check most likely to have been skipped.
  3. Wrong passcode returns the same message and timing as an unknown name.
  4. Edit from two devices under two names; confirm the margin shows the right person on each block.
  5. curl the document with a valid cookie and confirm X-Robots-Tag: noindex is on the response — see domain-wiring.
Rejected: per-person magic links, and why the passcode is not just lazinessthe argument, in case it comes up again

Magic links give real per-person identity, revocability, and no shared secret to leak. They also need four email addresses (Ed's and Ben's are not in this project), an email sender configured on a new domain with no DKIM history — so the first send goes to spam — and a token flow to build and test. That is most of a day, and the failure mode is a friend who cannot get in on the Thursday night when the car decision is being made.

The passcode is chosen because the trip is in three days and the threat model is a crawler. If this document outlives the trip, revisit; nothing here forecloses it, because the cookie already carries a name and the socket already checks it.
