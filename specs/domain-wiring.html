Wiring iceland.rosettawang.org

Status: done done · created Aug 5, 2026 · shipped & verified Aug 5, 2026 · priority 5

Rosetta, Aug 5, 2026: "wire to iceland.rosettawang.org i just bought on namecheap." The domain is registered and pointing at nothing. Cloudflare has never heard of it.

This spec is first in the order and is not the first thing to finish

It sorts to the top because the slow part is a stranger's DNS cache, not because the document depends on it. Kick off the two account steps below now; then build live-doc-core against iceland-doc.<subdomain>.workers.dev while propagation happens in the background.

Do not let this gate sharing the link. If Thursday arrives and the nameservers have not flipped, send the friends the workers.dev URL. It is the same Worker; the custom domain is a nicety, and the trip is not.

Live as of Aug 5, 2026 — what was actually done, in order

  1. Zone added to Cloudflare via the dashboard (the CLI token cannot — verified refused).
  2. Namecheap → Custom DNS → cullen.ns.cloudflare.com, ryleigh.ns.cloudflare.com, saved.
  3. Nameservers visible on a public resolver ~4.5 minutes later. Namecheap warns "up to 48 hours", which is a worst case for a domain that has never had traffic, not an estimate.
  4. routes added to wrangler.jsonc and deployed. Cloudflare created the proxied record and issued the certificate itself; no record was added by hand.

Against the live domain: / and /packing both 200, x-robots-tag: noindex present, TLS verified, and all four crew words resolve to the right person while a bare first name is rejected.

The trap in step 4: declaring a route silently turns workers.dev OFF

wrangler deploy mentions it in a passing warning and proceeds. For the minutes between that deploy and DNS propagating, there was no working URL at all — the old link had been disabled and the new one did not resolve yet. Fixed by setting "workers_dev": true explicitly.

Keep it that way. The workers.dev URL is what still works if anything goes wrong with the domain while four people are in Iceland relying on the document.

Login pass — two items, both hers, five minutes total

  1. Add rosettawang.org to Cloudflare. dash.cloudflare.com → Add a site → rosettawang.org → Free plan. There is nothing to import; the zone is empty. Cloudflare then shows two assigned nameservers — those are the values step 2 needs, and they are account-specific, so they cannot be written down here in advance.
    Why she has to: creating a zone needs zone.create, which the CLI token was tested against and refused. This is the token's own limit, not a policy choice.
  2. Point Namecheap at them. namecheap.com → Domain List → rosettawang.org → Manage → Nameservers → Custom DNS → paste both Cloudflare nameservers → save (the green tick, easy to miss).
    Why she has to: Namecheap is a registrar account with her login, and there is no API key configured for it.

Then it is hands-off. Cloudflare emails when the zone goes active; typically under an hour on a fresh domain with no prior nameservers to expire, occasionally several. Nothing about this is worth watching — go build the document.

What happens after the zone is active — no further human needed

The custom domain is declared in wrangler.toml and applied by a deploy. Cloudflare creates the proxied DNS record and issues the certificate itself; there is no record to add by hand and no Namecheap DNS to configure, because the nameserver change moved DNS to Cloudflare wholesale. 

[[routes]]
pattern = "iceland.rosettawang.org"
custom_domain = true
npx wrangler deploy

Then verify it for real, in this order

dig +short NS rosettawang.org                      # expect the two Cloudflare NS
dig +short iceland.rosettawang.org                 # expect Cloudflare proxy IPs
curl -sI https://iceland.rosettawang.org | head -1 # expect HTTP/2 200, not 301/403/526

Check the certificate, not just the status line. A brand-new custom domain serves 526 or a browser warning for a few minutes while the edge cert is issued, and that window is long enough to look like a broken deploy and send someone editing config that was already correct. If curl is happy but Safari is not, wait five minutes before touching anything.

One thing to get right the first time: this is a public URL with no index

A trip document at a guessable subdomain, containing four people's flight numbers, arrival times and where they are sleeping, should not be in a search index. Serve X-Robots-Tag: noindex, nofollow from the Worker on every response and ship /robots.txt with Disallow: /. That is two lines during the build and an unpleasant email to write later. Access control itself is access-and-identity; this is only the crawler.

Rejected: keeping DNS at Namecheap and pointing a CNAMEwhy the nameserver move is the lesser hassle

A Worker can be reached by a CNAME from an external DNS provider, but Cloudflare custom domains want the zone in the account to issue the certificate and to route without the request leaving for Namecheap's resolvers first. Doing it the CNAME way means a CNAME-flattening problem at the apex later, a manual certificate story, and a second dashboard to remember. The nameserver move is one paste, once, and afterwards every subdomain of rosettawang.org is one line of wrangler.toml forever — which matters the moment there is a second thing on this domain.

It is also the pattern already running twice in this account: whrfund.org and laurelate.com are both full Cloudflare zones.
