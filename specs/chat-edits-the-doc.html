Asking for a change in words

Status: done done · created Aug 5, 2026 · shipped & verified Aug 5, 2026 · priority 40

Rosetta, Aug 5, 2026: "make a chat that adds text input which changes the contents." A panel on the right. You type what you want; the document changes.

What this can do that the hover comment can't

The hover comment can only change something that already exists — you have to be pointing at it. The chat is the only way to add something that isn't there yet, and that is most of what this document still needs: there is no lodging section, no car booking, no arrival times for Ed and Ben. "Add a Reykjavík lodging section with three options under $400" has nothing to hover over.

That is the split worth teaching: comment to fix, chat to add. The empty-state examples in the panel are all additions for exactly this reason.

The panel

  • Closed by default, behind a violet "Ask Claude" pill bottom-right. The document is the product; the chat is a tool you reach for.
  • Empty state teaches by example, with three real requests against this actual trip rather than generic prompts. Someone who reads "Ed lands Aug 9 at 06:30 on FI614 — add him to the flights table" knows immediately what kind of thing to type.
  • Your message, then Claude's reply, then a count. "3 blocks changed" under the reply — because the reply says what it did and the count says whether it actually did it.
  • Enter sends, Shift-Enter newlines.
  • The remaining daily budget sits in the header once you've spent one, so running out is something you see coming rather than discover.

Where the changes appear

Not in the chat. No diff, no preview, no accept/reject. The edits land in the document behind the panel with a violet flash, and Undo in the status bar reverses the last one. A confirm step on every AI edit sounds safer and in practice trains people to click "accept" without reading — the undo is honest about how it will actually be used.

Cost: the chat sends the whole document, and that is a real number

Every chat message carries all 46 blocks — roughly 15k input tokens, about $0.08 a message at Opus 5 pricing. Against the account's $28.22 credit balance (checked Aug 5, 2026) that is a few hundred messages, which is fine for four people over eleven days and is not fine if the link leaks. Hence the per-person daily cap of 30 in access-and-identity, which is the actual spend control; this note is the reason it exists.

Scoping chat context the way the hover comment scopes it would need a retrieval step — pick the relevant sections, then edit — and that is a second model call and a new failure mode, for a document small enough that the whole thing fits comfortably. Revisit if the document doubles.

Photos done

Rosetta, Aug 6, 2026: "the chat should be able to take in photos." Paste a screenshot into the panel; Claude reads it and files what it says.

This is the fastest path from a fact existing to a fact being in this document

Almost nothing in this plan originates here. It arrives as a Blue Lagoon confirmation, a shift roster, an Icelandair booking on someone else's phone. The slow, error-prone step was always the human retyping an eleven-character booking reference into a chat box. A screenshot skips it, and a model transcribing a reference number is more reliable than a person doing it on a phone at an airport.

It also fixes the one thing chat could not do for other people. Ed does not have to describe his flight; he screenshots it. That is the difference between a request and a chore.

Resize in the browser, not on the Worker

A phone photo is 4 MB and 12 megapixels. The canvas pass caps the long edge at 1400px and re-encodes as JPEG at 0.82, which lands around 200–400 KB — and the model reads a 1400px screenshot exactly as well. Doing it client-side means the upload is small on campsite 3G, which is where this will actually be used. It strips EXIF on the way through, which is a free win: photos carry GPS.

Ceilings on the Worker anyway — four images, ~3.7 MB decoded each, four allowed media types — because the browser is not the only possible client and a resize can silently fail. Anything failing those is dropped silently rather than failing the message: refusing all four screenshots because the fourth was a HEIC loses the three good ones and the thing the person was trying to say. Claude names what it saw in its reply, so a photo that did not make it is visible in the answer.

Three ways in, because the fast one is invisible

  • Paste is the real interaction: screenshot, ⌘V, Enter. No file dialog at any point.
  • Drop anywhere on the panel, not on the 58px tray. Aiming a dragged file at a thumbnail strip is a test of motor control nobody signed up for.
  • The 📷 button, which exists mostly so people discover that any of this is possible. Same reason the empty state now says so in a sentence.

A photo with no message is a message

"Here, deal with this" is the most likely way this gets used, so an empty instruction with an attachment is not treated as an empty request — it gets an explicit "work out what this is and put it where it belongs". Without that the model describes the image back at you, which is useless.

Rule 4 — never invent a fact — is where this earns or loses trust

The failure mode is specific and bad: a confidently wrong confirmation code. A blurred digit read as an 8 is worse than an unread one, because someone stands at a desk with it. So the system prompt says to transcribe character for character, and where a value is cut off or unreadable, write the readable part, mark the rest unread, and say so in the reply.

Verified Aug 6, 2026: a mock Icelandair confirmation came back with the reference, flight number, route and both dates exact — and zero ops, because the message was a question.

Not doing: photos on the hover comment

The comment path is deliberately cheap — it sends one section, not the document. Attaching an image to it would roughly double that request for a case that barely exists: you comment on a block because you can see what is wrong with it, not because you have a screenshot of it. Chat is where new facts arrive, so chat is where photos go.

Verification

  1. "Add a Reykjavík lodging section with three placeholder options" → new blocks appear in a sensible section, in house style, for everyone.
  2. Ask a question rather than an instruction → an answer, and nothing in the document moves.
  3. A request touching two sections → both change, count says 2 or more.
  4. Spend the daily cap → the panel says so plainly and direct editing still works.
  5. Send with no key set → a message saying the key is missing, not a silent failure.
  6. Paste a screenshot of a confirmation → thumbnail appears, sends, and the reference comes back character-perfect.
  7. Attach a photo with no text at all → it gets filed somewhere sensible rather than described back.
  8. Send a screenshot with a value deliberately cropped in half → the gap is stated, not guessed.
  9. Attach five photos → the fifth is refused in the panel, before anything is sent.
  10. Send, then immediately send again → the second message carries no photos from the first.
