Editing it like a document

Status: done done · created Aug 5, 2026 · shipped Aug 5, 2026 · priority 20

Rosetta, Aug 5, 2026: "allow for direct editing like changing text or deleting as if its a live document." Click a line, change it, it is changed for everyone. No edit mode, no save button.

Why this one ships before the AI features, even though the AI features are the interesting part

It is the only editing surface with no dependency on an API key, a balance, or a model being up. If the Anthropic key never gets pasted, a document you can click into and correct is still the thing that replaces the group chat. The AI paths are an accelerant on top of a document that already works, and building them first would produce a document that only works when it is being paid for.

  • Hover a block: a 1px left rule appears and a handle strip fades in at the margin — drag (⋮⋮), comment (💬, see hover-comment-to-edit), delete (✕).
  • Click text: that block becomes contenteditable in place. The caret lands where the click landed. Nothing reflows — the editing state must not shift the page by a pixel, or every edit begins with the reader losing their place.
  • Blur or Esc: save. There is no save button, and there is no autosave timer either — see below.
  • ⌘B / ⌘I / ⌘K: bold, italic, link. That is the entire toolbar.
  • Enter at the end of a block: create a new empty block after it, already focused. This is how anything gets added.
  • Delete: ✕ removes the block with a 6-second undo toast. No confirmation dialog — a dialog on every delete trains people to dismiss dialogs, and the undo is strictly better because it also covers the deletes nobody meant to do.

Saving: on blur, plus a 2-second idle flush

Blur-only loses work when a phone browser is backgrounded mid-sentence, which will happen at an airport. Keystroke-level sync would need the CRDT that live-doc-core deliberately does not have — broadcasting every keystroke as a whole-block replace means the other person's screen redraws under their cursor while you type. So: flush 2 seconds after typing stops, and on blur, visibilitychange and pagehide. Someone else sees your paragraph land a couple of seconds after you finish it, whole, which is the right granularity for a trip plan.

The block you are editing must not be overwritten under your cursor

While a block is focused locally, incoming block frames for that block are held, not applied. On blur, if a held version exists, the save is submitted with the original baseRev, the server rejects it, and both versions are shown side by side with "keep mine / keep theirs". Every other block keeps updating live behind you.

Skipping this produces the single worst bug available in this design: text vanishing mid-sentence because someone across the Atlantic saved the same card. It is a dozen lines and it is not optional.

Tables, because half the document is tables

Flights, festival timings, activity prices, the eclipse clock. Cells are individually contenteditable; the block that saves is still the whole table. Row-level handles on hover at the row's left edge: + below, ✕ to remove. No column operations — adding a column to a six-column table on a phone is not a real workflow, and the AI paths can do it on request ("add a confirmation-number column") for a fraction of the effort.

Paste is where the document gets wrecked

Everything arriving in this document comes from somewhere else: a confirmation email, an Airbnb page, a Google Doc. Pasting any of those into contenteditable drops in font tags, inline colours and background styles, and two paragraphs of that makes the page look broken in a way that is tedious to undo by hand.

So: intercept paste, take text/html, run the same allowlist the server runs (live-doc-core), insert the result. Shift-paste inserts plain text. The server sanitises again on receipt — the client-side pass is for what the user sees, the server-side pass is what makes it safe.

Mobile, which is where this will mostly be used

Three of four people will read this on a phone, and at least one edit will happen on airport wifi.

  • Hover does not exist. Long-press (400ms) opens the handle strip as a small sheet; tap enters editing.
  • Handles are 44px targets even though the resting visual is a thin strip.
  • iOS Safari scrolls the caret under the keyboard on a long block — scroll the focused block into view on focus and on resize, or editing a card near the fold is unusable.
  • No drag-to-reorder on touch. Long-press → "Move up / Move down" in the sheet. Touch drag inside a scrolling document fights the scroll and loses.

Verification

  1. Edit a paragraph on a phone; confirm it lands on the laptop within ~2s of stopping typing, without a reload.
  2. Focus a block on device A, edit and save the same block on device B, then blur A. Expect the side-by-side keep-mine/keep-theirs, and expect A's typing to still be there.
  3. Paste a chunk of a real Airbnb page into a card. Confirm no colours, fonts or backgrounds survive and the layout is unchanged.
  4. Add a row to the Flights table on a phone; check it on the laptop.
  5. Delete a block, wait for the toast to expire, reload — it stays deleted. Delete another, hit undo, reload — it is back.
  6. Background the tab mid-sentence on iOS, reopen: the sentence is saved.
