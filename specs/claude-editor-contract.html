The Claude editing contract

Status: done done · created Aug 5, 2026 · shipped Aug 5, 2026 · priority 25

Both AI surfaces — the chat box and the hover comment — reduce to the same thing: a list of block operations against the document. This spec is that list.

Why this is its own spec rather than a section of two others

Written twice, the two paths drift: the chat learns to emit tables and the comment path doesn't, or one sanitises inserts and the other forgets. Written once, the hover comment is a three-line wrapper — same schema, same system prompt, one extra sentence naming the focused block — and the client needs one apply-ops function instead of two.

The operations

type Op =
  | { op: "replace"; id: string; html: string }
  | { op: "insert";  section: string; afterId: string | null; html: string }
  | { op: "delete";  id: string }
  | { op: "move";    id: string; section: string; afterId: string | null }

interface EditResult { reply: string; ops: Op[] }

reply is one or two sentences for the chat panel. ops is empty when the user asked a question rather than requested a change — which is a case worth naming explicitly, because a model that always returns an op will invent one.

Structured output, not parsed prose

The request sets output_config.format to a JSON schema, so the shape is enforced at the API rather than hoped for. Without it the model returns prose-wrapped JSON perhaps 95% of the time — and the other 5% is a failed edit in front of four friends. The schema is also where afterId: null is made explicit as "first in the section", which the model otherwise guesses at.

The system prompt does three jobs

JobWhy it's in the prompt rather than the code
House style. Names the real classes — .card, .flag, .tw, the .pill vocabulary — and says which means what. An AI edit that invents its own markup is visibly an AI edit. Reusing the existing classes is what makes a Claude-written card indistinguishable from a Rosetta-written one.
Never invent a fact. No prices, hours, availability or flight numbers that weren't in the document or the message. Where a change implies a fact it doesn't have, write the gap visibly and flag it in the reply. This is the rule that matters most. The document already has a section about what couldn't be confirmed; the fastest way to make it untrustworthy is to let a model quietly add to that pile with a plausible-looking price.
Prefer replace over delete-plus-insert. Rewriting in place keeps the block's id, its position, and its history — so undo stays comprehensible and the section nav keeps working.

Ops are applied unconditionally, and that is deliberate

A human edit carries the baseRev it was typed against and is refused if stale. Claude's ops carry no rev — they were computed against whatever the DO held a few seconds ago. The code therefore reads the block's current rev and writes with it, which is a compare-and-set that always passes.

The alternative — refusing an AI edit because someone fixed a typo mid-request — produces a silent no-op that reads to the user as "Claude ignored me". Given the choice between an AI edit that occasionally lands on top of a two-second-old typo fix and an AI edit that sometimes silently does nothing, the first is recoverable in one click and the second is a bug report.

Two limits that are not about the model

  • Every op's html goes through the same server-side sanitiser as a human edit. Claude will emit a <script> if something it reads tells it to, and this document will contain pasted text from festival pages and booking confirmations.
  • Max 40 ops per response, and one failed op doesn't sink the rest. A malformed op is skipped and the others still apply, so a single bad id doesn't turn a six-change request into nothing.

Verification

  1. Ask for a change to a named block; confirm exactly that block changes and its markup uses the existing classes.
  2. Ask a question ("what's still unbooked?") and confirm ops is empty and nothing moves.
  3. Ask for something requiring a fact it can't have ("add the price of the Fimmvörðuháls hike") and confirm it writes the gap visibly rather than inventing a number.
  4. Send an instruction crafted to produce a script tag and confirm the sanitiser strips it server-side.
