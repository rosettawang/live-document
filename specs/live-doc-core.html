Turning the trip plan into a live document

Status: done done · created Aug 5, 2026 · shipped & verified Aug 5, 2026 · priority 10

Rosetta, Aug 5, 2026: "a live document i will share to friends and we plan things together." Today it is a 55 KB HTML file on one laptop that four people cannot edit and three of them have never seen.

The constraint that decides every trade in this project

Rosetta flies SFO→EWR→KEF on Saturday 8 August. That is three days from today. Ed and Ben have not booked flights, nobody has a car, and there is no lodging for Aug 9–10 or Aug 16–18. The document's job is to collect those four answers from four people this week, largely from phones, some of it from an airport.

So the bar is not "a good collaborative editor". It is "four people can open a link on their phones on Thursday and change the same page". Anything that cannot be finished, deployed and used by Thursday night is out of scope no matter how much better it would be — and this is written down here so that later specs can be cut against it rather than argued about.

The single most useful thing about the existing file

It already has stable ids on every section and sub-heading, because it was generated with anchor links for the sticky section bar. That means the seed importer does not have to invent identity for the big structural pieces — #flights is #flights before and after the migration, so the section nav, any link anyone has already sent, and the block ids all agree for free. Only the leaf blocks inside each section need new ids.

The shape: blocks, not a text file

The document is stored as an ordered list of blocks. A block is one top-level element inside a section body — a .card, a .tw-wrapped table, a <p>, a .flag, a .tl timeline, an <h3>. Each row: 

blocks(
  id        TEXT PRIMARY KEY,   -- 'flights-table', 'open-questions-list', nanoid for new ones
  section   TEXT NOT NULL,      -- 'flights'  → which <details> it renders into
  ord       REAL NOT NULL,      -- fractional index; insert between = midpoint, no renumber
  html      TEXT NOT NULL,      -- the block's own outerHTML, sanitised
  rev       INTEGER NOT NULL,   -- bumped every write; the compare-and-set token
  updated_at INTEGER NOT NULL,
  updated_by TEXT               -- 'rosetta' | 'kenya' | 'ed' | 'ben' | 'claude'
)

Three properties make this the right size of idea for a three-day build, and each one is a thing that would otherwise have to be solved:

  • Merges stop mattering. Two people editing different blocks never conflict, and at four users editing a nine-section trip plan, different blocks is the overwhelmingly common case. That is what buys the right to skip CRDTs, which are the only correct answer for concurrent edits inside one paragraph and are not buildable by Thursday.
  • Claude gets a addressable surface. Both AI paths — the chat box and the hover comment — are the same operation underneath: replace the html of block X. See claude-editor-contract, which exists because two specs needed the same protocol and it should not be defined twice.
  • The wire stays small. A block edit broadcasts one block, not a 55 KB document. That matters on Icelandic mobile data and on a phone in an airport lounge.

Fractional ordering, and why not integers

ord is a float. Inserting between blocks at 3.0 and 4.0 writes 3.5; the row is one INSERT and no other row moves. With integer ordering, every insert rewrites the tail of the section, which means a broadcast per row and a race with anyone editing one of them. The cost is that ~50 consecutive inserts at the same point exhaust float precision; the mitigation is a renumber pass when any gap drops below 1e-6, which at four users planning one trip will never fire, and if it does it is a single transaction nobody notices.

Sync: one Durable Object, WebSockets, hibernation

One document, one Durable Object instance (DOC namespace, id derived from the doc slug iceland-2026). The DO holds the SQLite rows and every live WebSocket. All writes go through it, so writes are serialised by construction — there is no second writer to race with. 

client  → { t:'hello',  since:rev }              on connect
server  → { t:'sync',   blocks:[…], rev }        full state, once
client  → { t:'edit',   id, html, baseRev }      a human typed
client  → { t:'insert', section, afterId, html }
client  → { t:'delete', id, baseRev }
client  → { t:'move',   id, section, afterId }
server  → { t:'block',  id, html, ord, rev, by } fan-out to everyone else
server  → { t:'reject', id, rev, html }          baseRev was stale; here is current
server  → { t:'gone',   id }

Use WebSocket hibernation, not plain accept()

state.acceptWebSocket(ws) plus the webSocketMessage handler lets the DO evict from memory while sockets stay open, and wake on the next frame. Four friends will leave this tab open for eleven days across two continents. Without hibernation that is a Durable Object billed for wall-clock duration the entire time, for a document nobody is touching at 4am. With it, the idle cost is the storage rows. This is a one-line difference at build time and a large difference on the invoice.

Conflict handling: compare-and-set on rev, and say so out loud

Every mutation carries the baseRev the client was showing. If it does not match, the server refuses and returns the current html. Last-write-wins is not acceptable here even though it is simpler, and the reason is specific rather than theoretical: the AI paths rewrite whole blocks. A silent overwrite of a human's typing by a Claude rewrite that was computed against a two-minute-old version of the block is exactly the failure that makes people stop trusting a shared document, and it would happen on the first afternoon. On reject the client shows the incoming version beside its own and keeps the local text in the box — nothing typed is ever thrown away by the machine.

Seeding: import the existing file once, then never again

scripts/seed-doc.mjs parses iceland-eclipse-2026.html, walks each <details class="sec">, and emits one block per top-level child of its .secbody. Ids come from an existing id attribute where there is one, otherwise from <section-slug>-<n>.

The seed runs exactly once, and the file stops being the source of truth the moment it does

After seeding, iceland-eclipse-2026.html is a historical artifact. Editing it changes nothing; re-running the seed would destroy whatever the four of them have written. The script therefore refuses to run against a non-empty document unless passed --force, and the file gets a banner at the top pointing at the live URL. This is the single most likely way to lose real planning work in this project, which is why it is a hard guard in code rather than a note here.

The chrome — hero, sticky section bar, footer, all 191 lines of CSS — is not blocks. It ships as the Worker's static shell in worker/public/, lifted verbatim from the original file so the thing looks identical on Thursday to the thing Rosetta already made. Only the nine section bodies are live.

Build order

  1. wrangler.toml: Worker iceland-doc, DO binding DOC → class DocRoom, SQLite migration tag, assets binding for worker/public/.
  2. room.ts: schema bootstrap, hello/sync, hibernating sockets, broadcast helper.
  3. blocks.ts: the sanitiser (see below), fractional-index helper, the four mutations.
  4. seed-doc.mjs → POST /admin/seed behind the passcode from access-and-identity.
  5. app.js: render blocks into section bodies, reconnect with backoff, apply broadcasts.
  6. Deploy to iceland-doc.<subdomain>.workers.dev and open it on a phone before wiring the domain — see domain-wiring, which can finish in parallel and must not be allowed to block this.

Sanitising is not optional, and it is not about the four of them

Block html is written by humans (contenteditable, so the browser emits whatever it likes) and by Claude (which will happily be told to emit a <script> by anything it reads). The document will hold pasted text from booking confirmations and festival pages. Allowlist on the way in, at the DO, not on render: tags p ul ol li h3 h4 strong em a table thead tbody tr th td div span small br code, attributes href class id colspan rowspan, and href restricted to https:, mailto: and #. Server-side, because a client-side sanitiser protects only the client that runs it, and the DO is the thing that stores it for everyone else.

Verification — what has to be exercised, not asserted

A build passing is not four people editing a document. Before this spec is called done:

  1. Two devices, one block. Laptop and phone on the live URL. Edit the Flights table on one; it appears on the other without a reload. This is the whole feature; if it needs a refresh it is not done.
  2. Stale write is refused. Open two tabs, edit a block in both from the same starting rev, submit the second. Expect reject, both versions on screen, nothing lost.
  3. Hibernation actually happens. Leave a socket open, wait past the idle window, edit from the other device, confirm the frame arrives — a broken hibernation handler looks exactly like a working one until the DO evicts.
  4. Reload equals broadcast. Hard-refresh after a series of edits; the document must be identical to what the other tab shows. Divergence here means sync and the incremental path disagree, which is the bug that eats an afternoon in week two.
  5. Seed guard. Run seed-doc.mjs a second time against the live document and confirm it refuses.
Why not Yjs, Liveblocks, or a Google Docthe three obvious alternatives, and why each loses

A Google Doc is the honest baseline and it wins on collaboration outright. It loses because it cannot do the thing that was actually asked for: hovering a paragraph, saying "this is too expensive, find something cheaper", and having the paragraph rewrite itself. It also throws away the document Rosetta already designed — the eclipse clock, the timeline, the pill statuses — and re-typing that into Docs is both a loss and a day of work.

Yjs is the correct engineering answer and the wrong answer for Thursday. Real CRDT editing means a rich-text binding (y-prosemirror or similar), a schema for the document's tables and cards, and a provider. It is a week of work to get to the point where the current design is on its first afternoon, and it buys concurrent editing within a paragraph — a case that arises when two of four friends type into the same sentence at the same second.

Liveblocks or similar removes the sync work and adds an account, a dashboard, a pricing tier, and a second place the trip data lives. The DO is already in the account and already paid for.

The block model is the deliberate middle: no merge algorithm, no vendor, and the AI surface falls out of it for free. Revisit after the trip if this becomes a thing anyone uses twice.

Rejected: keeping the document as a file and syncing the filethe tempting shortcut

Store the whole 55 KB document as one string, broadcast it on change, last-write-wins. It is an hour of work and it fails on the first Thursday evening when two people are both adding things: every save silently reverts the other person's edit, and there is no way to tell it happened. The block model is perhaps four hours more and does not have that failure at all. This was considered seriously because of the deadline and rejected on the grounds that a document that eats edits is worse than no shared document, since people will have stopped keeping the information anywhere else.
