The packing list turned out to be the better argument for this design than the trip plan

It is 37 blocks of tent-anchoring arithmetic and 11 of packing items — a document whose entire content is numbers someone will want to argue with ("is 69 kgf per anchor right if we only bring eight pegs?"). That is exactly the hover-comment interaction, and it would have been a shame to leave it as a static file next to a live one.

How it works — three small pieces

  1. The build emits one shell and one seed per document. scripts/build-shell.mjs loops a DOCS array; adding a third page is four lines and no new code.
  2. Each page declares which document it is via <meta name="x-doc">, and the client appends ?doc= to its socket and API calls. The Worker maps that to DOC.idFromName("doc:<slug>") — a separate Durable Object, with its own SQLite, its own history and its own seed.
  3. The sticky section bar carries the cross-link — "Packing list →" on one, "← Trip plan" on the other — placed before the collapse-all button so it reads as navigation.

An unknown ?doc= falls back to the trip plan rather than creating a new document

DOC.idFromName() will happily mint a Durable Object for any string, so a typo'd or hand-edited query parameter would otherwise create an empty document that looks like the real one having lost everything. The Worker allowlists the two known slugs; anything else is the trip plan.
